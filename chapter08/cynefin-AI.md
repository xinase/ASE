#拿捏克奈文模型 Complicated 与 Complex 的分界线

## 一、Cynefin 模型：大多数人只是记住了名词

在很多关于 AI 能力的讨论中，Cynefin 框架经常被引用——人们会说“这是 Complicated，那是 Complex”——但多数引用只停留在分类层面。你问他们“为什么围棋是 Complicated 而软件维护是 Complex？”，他们往往答不上来，或者给出一堆抽象的、不可验证的定义。

事实上，Cynefin 框架的真正价值不在于给问题“贴标签”，而在于帮助我们做出**动态的、可操作的判断**——一个系统在什么时候可以被降维为“可分析”的 Complicated，什么时候必须被视为“只能通过试错来感知”的 Complex，以及什么时候已经滑入了“无人能预测”的 Chaotic。而判断能力，恰恰需要通过具体的工程案例来训练。

我们沿着一个难度阶梯，从最简单到最复杂，逐步推进：

| 任务 | 本质 | 属于 |
|:---|:---|:---|
| **Hello World** | 在屏幕上显示一段文本 | Complicated |
| **实现 `ls` 命令** | 输入参数，输出文件列表 | Complicated |
| **在 macOS 上实现 Notepad** | 文本编辑 + 文件读写 + 编码兼容 | 介于两者之间 |
| **在 macOS 上实现 Paintbrush** | 实时绘图 + 交互反馈 + 视觉体验 | Complex |
| **维护一个 10 年历史的开源软件** | 历史契约 + 社区治理 + 持续演化 | **Chaotic 或高度 Complex** |

为了简化讨论，我们定义：**“模仿 Notepad 和 Paintbrush 在 Windows 上的行为”就是它们的 spec。** 我们甚至可以让一个强大的 AI 在 Windows 上运行并观察这些程序，得到两份 spec——一份是**技术 spec**（菜单、快捷键、API 调用序列、像素输出），另一份是**人类用户期望值的 spec**（“手感”、“直觉”、“流畅度”的隐含标准）——然后把这两份 spec 都传递给 macOS 上的 AI 去执行。

这个阶梯会反复出现。先记住它，然后我们往下走。


## 二、AlphaZero 的启示：它不依赖任何人类棋谱，也从未实现过 GUI

在深入讨论之前，有必要先澄清 AlphaZero 和早期的 AlphaGo 之间的区别。

AlphaGo 的训练分为两个阶段：首先用大量人类棋谱进行监督学习，让模型学会“像人一样下棋”；然后再通过强化学习自我对弈来提升。而 **AlphaZero 是完全不同的**——它从零开始，只被输入围棋的基本规则（棋盘大小、落子方式、胜负判据），**不依赖任何人类棋谱**。它的起点是一张白纸。国际象棋版本在 9 小时内就超越了人类顶尖水平，围棋版本则在 13 天内完成。

第一天的 AlphaZero，水平极低，甚至下不过业余初学者。但所有研究者都知道：只要继续运行现有的算法，给它几十个小时，它一定会超越人类顶尖棋手。

为什么我们能如此确定？

因为 AlphaZero 面对的是一个 **Complicated** 问题：
- 目标函数固定（“赢棋”——胜率是一个可计算的标量，不随时间漂移）；
- 反馈即时且明确（每盘结束，胜负结果立即可知，直接作为奖励信号回传）；
- 状态空间虽大（10¹⁷⁰ 种棋局），但封闭且有边界（19×19 棋盘，规则永不改变）；
- 每一步迭代都在**单调地优化胜率**，不会倒退。

更重要的是：**AlphaZero 的“下棋”行为，本质上是“棋盘状态 → 落子位置”的映射。** 它是一个协议执行者，而不是一个“体验”提供者。AlphaZero 不需要理解“围棋的美感”、“对手的心理”、“落子的节奏”——它只关心一个数字：胜率。它从没实现过一套 GUI 来显示棋盘，也从不关心棋子画得好不好看、落子动画是否流畅——它只是独立完成数学层面的映射计算。

事实上，实现一个“将棋谱状态实时显示为 GUI 棋盘”的程序，虽然工作量不小（涉及图形渲染、事件处理、动画效果），但它本身是 **Complicated 且 straightforward 的映射任务**：给定当前的棋盘状态（19×19 的矩阵，每个点标有黑/白/空），输出对应的屏幕像素。它没有“交互循环”，没有“手感”，没有“用户期望漂移”——它只是把数据翻译成像素。这属于 Complicated 的范畴，AI 完全可以独立完成。


## 三、现在，把同样的逻辑套在 Paintbrush 上

假设第一天，AI 开始开发 macOS 上的 Paintbrush。它生成了一份代码，能编译、能运行、能用铅笔工具画几条线——但还远远不及 Windows 画图的质量。

这时候我们追问：**给它更多时间、更多算力，它会像 AlphaZero 一样，最终完美复刻 Windows 画图吗？**

答案大概率是“不会”。原因不在于算力，而在于问题的本质：

| 维度 | AlphaZero（Complicated） | Paintbrush（Complex） |
|:---|:---|:---|
| 目标函数 | 固定（胜率） | 漂移（“用户觉得好用”无法量化） |
| 反馈信号 | 即时且明确（胜负） | 模糊且延迟（“手感”需要人类主观判断） |
| 状态空间 | 巨大但封闭（19×19 棋盘） | 开放且无限（用户操作序列 + 系统响应循环） |
| 收敛性 | 单调趋近最优 | 可能振荡、倒退、永不收敛 |
| 时间的作用 | 帮助遍历状态空间 | 帮助生成更多历史债务和新依赖 |

AlphaZero 的“差”是**量的差**——它的策略不好，但在有限空间内，它知道自己在找什么。Paintbrush 的“差”是**质的差**——它甚至不知道“完成”长什么样，因为“用起来顺手”不是一个可以被测试脚本捕获的布尔值。


## 四、一个看似可行的方案：用 AI 观察 Windows 画图，然后把行为传给 macOS 上的 AI

有人可能会反驳：“我们可以让一个强大的 AI 在 Windows 上运行 Paintbrush，充分观察并记录它的所有操作——包括菜单、快捷键、鼠标交互、像素输出——然后把这些记录作为规格说明（spec），传递给 macOS 上的 AI 去实现。这不就是一个完整的闭环吗？”

让我们仔细拆解这个方案。

**什么是“规格说明”（spec）？**

在这个方案中，spec 实际上包含两个层次：

- **技术 spec**：菜单项列表、快捷键映射、文件格式支持、API 调用序列、鼠标事件的坐标和时序、屏幕像素的变化……这些是“可被记录”的东西，AI 可以在 Windows 上完整地捕获它们。
- **人类用户期望值的 spec**：用户在使用 Paintbrush 时“期望什么感觉”——线条是否跟手、撤销是否自然、缩放是否平滑、颜色选取是否直观……这些是“**不可被记录**”的东西，因为它们只存在于用户的感知和判断中，而不存在于任何日志文件或截图中。

**技术 spec 可以被完整记录和传递。但人类用户期望值的 spec 无法被任何 AI 捕获——因为它不在屏幕里，也不在日志里，它只在用户的体验里。**

这就是为什么这个方案只能解决一半的问题：它能帮助 macOS 上的 AI 实现“功能列表”级别的复刻——菜单有了、快捷键有了、文件格式支持了——但无法实现“用户体验”级别的复刻。用户在 Windows 上画一条线时感受到的那种“跟手感”，在 macOS 上可能完全不一样，因为底层的事件调度机制、图形渲染管线、输入设备驱动都不同。而 AI 没有任何方式知道“这种差异是否被用户接受”——它没有判断力，只有执行能力。


## 五、一个子集是可以做的：“打开一个 BMP 文件并显示”

那么，在这个庞大的任务中，有没有什么是 AI 可以完全独立完成的？

答案是肯定的。例如：**实现 Paintbrush 的“打开一个 BMP 文件并显示”这个子功能。**

为什么这个子功能可以？

| 维度 | “打开 BMP 并显示”的情况 |
|:---|:---|
| 输入 | BMP 文件的二进制数据（格式有公开的完整规范） |
| 输出 | 屏幕上显示的像素阵列 |
| 映射关系 | BMP 解码是一个确定性的流程：文件头 → 信息头 → 调色板 → 像素数据 |
| 交互性质 | **零交互**——用户只需要“打开文件”这一个离散操作，然后系统独立完成解码和渲染 |
| 判断标准 | “显示的图像是否与文件内容一致”——可以用截图比对自动验证，不存在模糊空间 |

这个子功能是一个纯粹的 **Complicated 映射**：输入 BMP 字节流，输出像素阵列。它不涉及“手感”，不涉及“交互循环”，不涉及“用户期望漂移”。AI 可以读 BMP 规范文档，然后实现解码器，然后用测试脚本验证正确性——整个过程都可以自动化，而且收敛时间可预期。


## 六、如果 Paintbrush 可以被拆分为有限个 Complicated 模块，那是不是意味着整件事可以在多项式时间内完成？

这是整个讨论中最关键的问题。

如果我们把 Paintbrush 的所有子功能都列出来——BMP 解码、PNG 编码、铅笔工具、矩形工具、颜色选择器、撤销栈、文件保存对话框、缩放显示……——并且每一个子功能都是一个明确的、边界清晰的 Complicated 映射，那 AI 逐一实现它们，似乎只是一个“工程量”的问题，对吗？

**理论上，如果这个列表是有限的、且每个子功能的 spec 是完整的、且子功能之间没有任何交叉依赖，那么 AI 可以在多项式时间内完成这个任务——这不是一个算法难题，只是一个枚举问题。**

但真实的 Paintbrush 不是这样工作的。问题出在三个地方，这三个地方也正是软件分形复杂度的体现：

**1. 子功能之间的依赖关系不是“树状”的，而是“网状”的**

“撤销”功能不是一个独立的模块——它依赖于铅笔工具、矩形工具、填充工具、缩放、粘贴等所有修改画布的操作。当 AI 实现撤销时，它必须理解所有其他工具的行为，并且在它们发生变化时同步更新撤销逻辑。这不是“依次实现 20 个独立模块”的问题，而是“在实现第 20 个模块时，需要回过头去修改前 19 个模块”的问题——而这个“回过头去修改”又可能引入新的依赖，形成无限递归。**这是依赖的分形：WBS 切开的不是蛋糕，而是海岸线——你放大任何一个微观任务，它里面都包含了整个软件生命周期**。

**2. 用户的操作组合是无限的，而 spec 只能覆盖有限的部分**

即使 AI 实现了所有“单个操作”的功能，真实的用户不会只执行单个操作。他们会：
- 画一条线 → 撤销 → 画一个矩形 → 缩放 → 撤销 → 再画一条线 → 保存 → 撤销 → 再缩放……
- 打开一个文件 → 旋转 → 裁剪 → 填充 → 添加文字 → 另存为 → 撤销五次 → 再保存……

这些操作组合产生了无限的“状态路径”，而 AI 的 spec 只能覆盖其中有限的一小部分（因为它只能记录有限次的操作）。当用户执行了一个“spec 中没有覆盖的组合”时，系统就可能崩溃、行为异常、或产生不符合预期的结果——而 AI 无法提前预判所有组合，因为它没有“模拟用户思维”的能力。

**3. 每个子功能都是映射，但“用户切换工具”本身不是映射——它是交互循环**

最重要的一点是：用户在不同的工具之间切换，不是“映射”，而是“交互循环”。用户用铅笔工具画了几笔，觉得不满意，切换到橡皮擦擦掉，然后又切回铅笔——这个“切换”的过程中，用户在不断地感知系统的反馈，并基于感知调整自己的下一步动作。这个循环本身无法被拆分为任何独立的子功能，因为它依赖于用户的实时判断和系统响应的实时一致性。

**所以，答案是这样的：**

- 如果“Paintbrush 的任务”被严格限定为“实现一个包含所有子功能的、非交互的、非组合的静态程序”，那它确实可以在多项式时间内完成——因为它只是一组 Complicated 映射的集合。
- 但如果“Paintbrush 的任务”被理解为“实现一个让用户感觉‘好用’的、能在无限操作组合下保持一致的、能随着用户期望演化的交互式应用”，那它**不是**一个可以在多项式时间内完成的问题——因为问题的边界本身在持续扩展，而 AI 没有任何方式判断“何时算完成”。

这就好比一个楼梯：实现单个台阶是简单的。但让用户在楼梯上行走时感到“每一步都踩得踏实”，这需要的不只是台阶本身——还需要栏杆的倾角、台阶的高度一致性、每一步的摩擦力、光线是否合适……而这些“体验”无法被分解为任何一组台阶的列表。软件的估算之所以永远不准，正是因为**在估算时，人脑在用认知尺度丈量地图；但项目交付时，CPU 在用微观的执行尺度一步步走完所有地貌**。


## 七、AI 能力的明显矛盾：能驱动复杂 Agent，却做不了一个 Paintbrush？

如果你观察当前 AI 的前沿应用，会发现一个令人困惑的矛盾：

- **一方面**，AI 可以驱动多个 Agent，通过 CLI（命令行界面）互相协作，完成非常复杂的任务——例如自动分析代码库、生成文档、部署服务、甚至自主地进行科研实验。16 个并行的 Claude 智能体用不到 2 万美元就构建出了一个可工作的 C 编译器。这些任务看起来极其“复杂”。
- **另一方面**，让 AI 独立实现一个 macOS 上的 Paintbrush，它却做不到。即使功能列表已经明确、参考实现就在眼前，AI 依然会在某个阶段卡住。

为什么？这个矛盾该如何解释？

### 区别在于：CLI 是“映射的世界”，GUI 是“交互的世界”

AI Agent 通过 CLI 协作时，所有交互都是**回合制的文本流**：

- Agent A 输出一段文本 → Agent B 读取这段文本 → Agent B 输出另一段文本 → Agent C 读取……
- 每一步都有明确的输入和输出，没有“实时反馈循环”，没有“手感”，没有“视觉体验”。
- 整个系统本质上是一个**映射链**：输入流经过一系列变换，输出流。这和 UNIX 管道没有本质区别。

而 Paintbrush 是一个**持续的交互循环**：

- 用户移动鼠标 → 系统在 16ms 内响应 → 用户看到反馈 → 用户调整手的动作 → 系统再响应……
- 这个循环的每一轮都依赖于上一轮的结果，而且“正确”的标准不是“输出是否匹配预期”，而是“用户是否感觉顺手”。
- 这个循环无法被拆解为一系列独立的映射，因为用户的行为本身就是动态的、不可预测的。

**CLI 世界是 Complicated 的：任务可以被拆解为一系列可枚举的映射，每一步都可验证。GUI 交互世界是 Complex 的：任务的核心是持续的双向实时交互循环，无法被简化为任何映射组合。**

所以，AI 能做复杂的 Agent 编排，是因为它在“映射链”的世界里工作——即使链条很长、分支很多，但每一步都是确定的、可验证的。而 Paintbrush 的核心不在“功能列表”，而在“交互体验”——这正是 AI 无法处理的部分。


## 八、为什么 AI 写“贪吃蛇”网页版可以手到擒来？

如果我们让 AI 写一个网页版的贪吃蛇游戏，它通常能在几分钟内生成一份完整可用的代码——HTML + CSS + JavaScript，键盘控制、碰撞检测、分数显示，全部到位。这又是为什么？

因为贪吃蛇和 Paintbrush 有着本质的不同：

| 维度 | 贪吃蛇（网页版） | Paintbrush |
|:---|:---|:---|
| **交互方式** | **离散事件驱动**——用户按方向键（上下左右），游戏状态更新，然后渲染下一帧 | **连续实时交互**——用户持续移动鼠标、拖动画笔，系统需要每帧响应 |
| **状态空间** | **有限且可枚举**——蛇的位置、食物的位置、方向、分数，全部是离散的整数坐标 | **无限且连续**——鼠标可以落在屏幕的任何一个像素上，用户的轨迹、速度、加速度都是连续的 |
| **反馈信号** | **明确**——“吃到了食物”是布尔值，“撞墙”是布尔值，“得分”是整数 | **模糊**——“手感好不好”、“线顺不顺”、“颜色对不对”都是主观判断，没有唯一答案 |
| **判断标准** | **功能正确即可**——蛇按方向移动、食物随机出现、游戏结束判定正确，就“完成了” | **体验必须达标**——功能即使全实现了，用户一句“感觉不对”，就得重来 |

更重要的是：贪吃蛇的用户交互是**离散的**——用户按一下方向键，蛇移动一格。在两次按键之间，系统不需要做任何事。这种离散的事件驱动模式，本质上仍然是“输入→输出”的映射——每一次按键都是一个独立的输入，输出是更新后的游戏状态。

而 Paintbrush 的用户交互是**连续的**——鼠标在画布上每移动一个像素，系统都要做出响应。用户不是“发出一条指令然后等待结果”，而是“持续地、实时地与系统互动”。这种连续交互无法被简化为离散的映射序列。

所以，AI 能轻松写出贪吃蛇，是因为它仍然在 **Complicated 映射世界**里工作——即使它涉及图形渲染和键盘事件，但它的核心逻辑依然是“离散输入 → 确定输出”。而 Paintbrush 的核心是“连续交互循环”，这超出了映射世界的边界。


## 九、MFC AppWizard 的启示：它比 AI 更早做到了“秒级生成 GUI”

如果你在九十年代用过 Visual C++ 的 MFC AppWizard，你可以在几分钟内，通过点选菜单生成一个完整的 MDI 或 SDI 应用——它有菜单栏、工具栏、状态栏、关于对话框、文档/视图架构——看起来甚至比 AI 生成的代码更“专业”。

那么，AppWizard 算是早期的人工智能吗？

不是。因为 AppWizard 做的只是 **“模板实例化”** ：它内置了几十套人类预先写好的骨架代码，你选一个，它就复制一份，替换掉类名前缀和应用名，然后输出一份可以编译的项目。

AppWizard 不会“理解”你的需求，不会“推理”你的业务逻辑，不会在你提了新需求后“重构”代码结构。它的能力在“生成骨架”那一刻就结束了——后续所有的业务逻辑、Bug 修复、功能演化，都需要人类来填。

而今天的 AI 代码生成器，虽然比 AppWizard 强大得多（它能合成全新的代码结构，而不是从固定模板里复制），但在一个关键维度上和 AppWizard 没有区别：**它只解决“起点”问题，不解决“后续的演化”问题。** 正如有人在讨论 AI 编程时指出：AI 消灭了 80% 的偶然困难代码，但剩下的 20%——那些涉及高并发、异常处理、系统一致性的本质困难——依然需要人类来面对。

AppWizard 可以生成一个“看起来像 Word”的骨架，但它生成不了一个“能替代 Word”的软件。同样，AI 可以生成一个“看起来像 Paintbrush”的起点，但它无法独自走完从“功能列表”到“经得起时间考验的软件”之间的漫长路程。


## 十、第五个层次：维护一个有 10 年历史、正在持续发布的开源软件

现在，我们来到这个阶梯的**最顶端**——也是最能体现 AI 能力边界的地方。

设想一个真实的场景：有一个开源软件，代码量约为 Linux 的 1%（约 300 万行），拥有 10 年历史，不少企业和个人用户正在使用，每三个月还在按期发布新版本。它有完整而公开的代码仓库、版本历史、PR 记录、邮件列表、CI/CD 工具链，以及一个长长的 issue list。现在，假设有无限算力的 AI 带领多个 Agent 接手了这个项目——**光凭 AI，能在 3 个月内发布一个新版本吗？**

答案极大概率是“不能”。而且，AI 不仅无法发布新版本，甚至可能把一个已经运行良好的项目**搞成混乱（Chaotic）状态**。

### 第 2 周：混乱全面爆发
### 第 3 周：Cynefin 框架中的 Chaotic 象限

此时系统已经滑入了 **Chaotic** 状态——问题太多、互相纠缠，因果关系完全混乱，没有清晰的“正确路径”。在 Cynefin 框架中，Chaotic 象限的唯一应对方式是：**先行动，建立秩序，把系统拉回 Complex 或 Complicated，再进行分析**。

但 AI Agent 无法“建立秩序”，因为建立秩序需要：
- 一个超越所有局部目标的**全局视角**
- 一个能够**承担责任**的决策者
- 一个能够**判断“足够好”**的验收标准

在人类的开源社区里，Linus Torvalds 或子系统维护者会说：“这个 PR 虽然技术上完美，但破坏了用户空间 ABI，不能合。那个 PR 虽然有点丑，但解决了 5 年前那个大客户的生产问题，先合，后续再优化。”

AI 无法做出这样的判断——因为它无法理解“商业妥协”、“历史债务”、“社区信任”这些概念。它只能看到代码，看不到代码之外的社会关系、经济成本和长期承诺。


## 十一、Windows Vista 的“Reset”：当人类自己也陷入 Chaotic

即使是人类世界一流公司的顶级工程师团队，在 Complex 系统中持续叠加“善意”的改动，也会将系统推入 Chaotic 的深渊，最终不得不通过“回到一个已知的稳定点”来重建秩序。

### 1. 充满善意的复杂性：Vista 的开发困境

在 Windows Vista 的开发周期中（早期代号 Longhorn），微软的工程师们充满了雄心壮志。他们引入了大量新技术：全新的图形驱动模型（WDDM）、更严格的安全机制（UAC）、以及被寄予厚望的下一代文件系统（WinFS，最终被搁置）。

这些都是 **“充满善意的代码”** ——每一个改动，在局部上都是合理的、优化的、面向未来的。但它们叠加在一起时，产生了惊人的连锁反应：

- 新图形驱动导致大量旧显卡蓝屏，破坏了与硬件厂商的隐性契约；
- 严格的安全机制与大量旧商业软件的运行逻辑冲突，破坏了用户生态的依赖；
- 整个代码库的依赖关系变得极度脆弱，修改一个核心组件，会导致数千个外围模块编译失败。

此时，系统已经滑入了 **Chaotic** 状态：因果关系完全混乱，修复 A 会同时引发 B 和 C，而 B 和 C 的修复又会回过头来破坏 A 的修补环境。没有一条清晰的“正确路径”可以走，因为它不是量变，而是**质变**——系统的复杂度已经超过了人类团队（即使是顶级团队）能够协同理解的认知带宽极限。

### 2. 唯一的解法：用“物理重置”强行建立秩序

在 Cynefin 框架中，应对 Chaotic 的首要原则是 **“Act - Sense - Respond”** （先行动建立秩序，再感知，再调整），而不是在混乱中试图分析。微软当时的行动，就是著名的 **“Longhorn Reset”** ：

他们放弃了已经投入数年心血的、代码量庞大的开发主线，**直接找回了 Windows Server 2003（一个已知稳定、有序的代码仓库）作为新的基线。** 然后，把那些真正必要的、经过严格测试和隔离的新特性，一点一点地、有节制地迁入这个新基线。最终，这个“重置”后的产品被命名为 Windows Vista（虽然还是背负了骂名，但至少是“可发布的”）。

微软的这个行动，在本质上，就是人类团队在面对 Chaotic 状态时所采取的“人类专属”策略：

| Cynefin 步骤 | Windows Vista 的实际行动 | AI Agent 为何无法做到 |
| :--- | :--- | :--- |
| **Act（强行建立秩序）** | 抛弃现有混乱代码库，回退到已知稳定的 Server 2003 基线。 | **无法定义“基线”**：AI 缺乏对“历史稳定性”和“商业可用性”的判断标准。它无法决定“放弃多少代码”才是可接受的。 |
| **Sense（感知）** | 严格测试迁入的新特性，感知它们是否稳定、是否与基线冲突。 | **无法设计验证边界**：AI 可以跑测试，但无法定义“哪些测试通过才算合格”。修复了性能，却破坏了兼容性，AI 无法感知这种取舍的合理性。 |
| **Respond（调整）** | 根据市场反馈，不断调整 Vista 的补丁和后续版本（最终推出 Windows 7）。 | **无法在失败中学习**：AI 没有“羞耻感”或“商业生存压力”，它不会因为 Vista 失败了就自主调整治理策略。它只会继续生成“技术上正确”的代码。 |

### 3. 这个案例对“AI 独立维护历史软件”的启示

回到第五层次的思想实验：如果一个拥有无限算力的 AI 团队接手了 Linux 内核（像微软接手自己的 Windows 内核一样），它在遇到 Chaotic 状态时，会怎样？

它大概率会**继续“优化”**，因为它的奖励函数只关心代码圈复杂度、测试覆盖率、编译通过率这些可计算的指标。当系统陷入死锁、回退循环时，AI 的唯一解法是**生成更多的代码去“覆盖”问题**——这就好比 Vista 团队在 Reset 之前，不断地打补丁、加抽象层，最终让系统变得更加臃肿和不稳定。

**人类专家之所以能在 Vista 这样的绝境中“壮士断腕”，是因为他们拥有 AI 永远无法具备的三样东西：**

1. **商业生存直觉**：知道“按时发布一个不完美但稳定的产品”比“追求技术完美”更重要。
2. **历史责任意识**：能够判断“哪些历史代码是必须保留的（因为有客户的真实依赖）”，哪些是可以割舍的。
3. **仲裁与决断力**：能够说“我们从头再来”，并为这个决定可能带来的市场损失承担责任。

AI 可以完美地执行“从 A 点到 B 点”的映射，但它永远无法“画出一条新的起点线”。因为**起点线的设定，永远是一个基于价值观和生存意志的决策，而不是一个基于算力的计算。** 这正是“拿捏”在最高层面的体现——决定何时“重置”以解决 Chaotic 状态，需要人类驾驭者做出基于生存判断的决策，而非基于代码分析的优化。


## 十二、回到 Cynefin：五个层次的完整图景

现在我们可以用五个任务来回答那个核心问题：

| 任务 | 核心挑战 | 能否被完全描述为“映射”？ | AI 能否独立完成？ |
|:---|:---|:---|:---|
| **Hello World** | 在屏幕上显示文本 | ✅ 是 | ✅ 完全可以 |
| **`ls` 命令** | 输入参数 → 输出文件列表 | ✅ 是 | ✅ 完全可以 |
| **Notepad** | 文本编辑 + 编码兼容 + 性能 | ⚠️ 部分是，部分不是 | ⚠️ 基本可用，但“完全”需人类介入 |
| **Paintbrush** | 实时绘图 + 交互反馈 + 视觉体验 | ❌ 不是 | ❌ 无法完全实现 |
| **10 年历史开源软件** | 历史契约 + 社区治理 + 持续演化 | ❌ 不是（还涉及社会契约） | ❌ 不仅做不了，还会搞成 Chaotic |

当软件的核心任务可以被完整描述为“输入 → 输出”的映射时，AI 可以独立完成，而且会做得很好。当软件的核心任务涉及“用户与系统之间的持续交互循环”时——用户的每一次动作依赖于系统的实时反馈，而系统的每一次响应又依赖于用户的感知和决策——AI 就无法独立处理。

而当软件的核心任务进一步上升到“维护一个拥有历史、社区和用户生态的活系统”时，AI 不仅无法独立完成，甚至可能把一个已经处于 Complicated 状态的系统**搞成 Chaotic**——因为 AI 缺乏社会意识、历史感知和仲裁能力，无法理解那些存在于代码之外的隐性契约。

这也是为什么 UNIX 的设计哲学（一切皆文件 + 管道组合）实际上是一种 **“主动把 Complex 降维为 Complicated”** 的策略：它将所有可能产生“交互循环”的部分都抽象为“文本流”，让系统从“持续的交互”退化为“一系列的映射”。而 AI 在处理 CLI 工具时表现出的强大能力，恰好说明它擅长的是映射，而不是交互循环。


## 十三、“拿捏”：AI 时代的人类工程能力

如果 AI 无法独立处理 Complex 系统，也无法应对维护历史软件这一 Chaotic 挑战，那一线专家是如何与 AI 协作的？

答案是：**专家通过“拿捏”（Harness）来动态地、持续地划分边界。**

专家做的事，不是“自己写所有代码”，而是：

1. **判断哪些地方可以交给 AI**——即判定哪些子区域已被成功降维为 Complicated 映射，可以安全地分治出去。这对应了 Cynefin 框架中从 Complex 向 Complicated 的“相变”——通过迭代实验，将“只能事后感知”的模式转化为“可分析可预测”的模式；
2. **看护好接口和契约**——通过自动化测试建立边界验证机制，确保 AI 的产出不破坏全局；
3. **哪些地方必须自己细看**——识别出仍然属于 Complex 的核心区域——涉及历史债务、用户依赖、价值权衡的部分，必须由人类裁决；
4. **持续重构，让软件始终处于“可被 AI 处理”的状态**——通过重构维护系统的低耦合度，使更多的区域可以被降维为 Complicated，从而扩大 AI 的能力区间。这需要在系统演化过程中保持**架构的宪法地位**，使其成为人与 AI 协作中“不会被改写的骨架”；
5. **在 Chaotic 状态下建立秩序**——当 AI 的多 Agent 协作已经陷入混乱时，人类需要介入，充当“最高法院”的角色，裁决冲突、撤销危险的修改、重新建立一致的方向。如 Vista 的 Reset 所示，有时候唯一的秩序重建方式就是“回到一个已知的稳定点”。

这个“拿捏”能力，本质上是 **AI 时代的 Harness（驾驭/套索）** ——它不是在制造更强大的动力源，而是在约束、引导、控制 AI 这股强大的力量，让它做功，同时确保它不偏离轨道。

| 旧模型：手艺人（Craftsman） | 新模型：驾驭者（Harnesser） |
|:---|:---|
| 用自己的双手直接打造每一件产品 | 用自己的判断力驾驭 AI 来生产产品 |
| 核心能力：肌肉记忆、手工技巧 | 核心能力：眼光、边界感、判断力 |
| 面对 Complexity 的反应：亲自动手 | 面对 Complexity 的反应：调整 Harness（重构边界、重新降维） |
| 面对 Chaotic 的反应：逐行调试 | 面对 Chaotic 的反应：建立秩序、恢复框架 |

**“拿捏”就是动态的分而治之** ——它不是一次拆分，而是一个随着系统、团队、AI 能力不断演化的持续治理过程。

专家通过持续拿捏，把 Complex 系统不断地拆解、降维、重构，让 AI 能够在 Complicated 区域内安全地、高速地工作——而人类则牢牢守住那些涉及判断、权衡、承担后果的核心阵地。正如 Fred Brooks 所言，软件的本质困难（Essential Complexity）无法通过任何“银弹”消除。AI 消灭了偶然困难的代码，却让本质困难在更高的抽象层次上以更隐蔽的方式浮现出来。这才是 AI 时代软件工程能力的真正内核。
