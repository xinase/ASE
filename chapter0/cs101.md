# AI 时代的软件第一门课怎么教：融入 CS2023 胜任力模型的教学重构

> **注**：这是一个建议初稿，针对的是理工科大一的第一门软件课程（CS 101），全面融入 ACM/IEEE-CS/AAAI **《计算机科学课程指南 2023》（CS2023）胜任力模型（Competency = Knowledge + Skills + Dispositions in Context）**。由于各高校生源起点与课时约束存在差异，方案采用“保底基线 + 进阶可选”的阶梯式设计，未必适合所有学校和专业，欢迎点评讨论。

## 序言：Learning by Doing，从解释世界到改造世界

马克思曾写道：“哲学家们只是用不同的方式解释世界，而问题在于改变世界。”

这句话在 2026 年有了新的含义。AI 正在成为有史以来最强大的“解释世界”的工具——它能解释一段代码的含义，能解释什么是多态、什么是内存泄漏，能解释架构设计的原理。而且，它会越来越擅长这件事。

但 AI 不擅长的是：在真实的工程约束下，做出决策并承担后果。

因此，这门 CS 101 的底层方法论是 **Learning by Doing**——不是通过听讲和阅读来“学习关于编程的知识”，而是通过亲手创造可运行、可维护、可协作的软件来让自己成长。我们不相信“先学完理论再动手”的线性路径；我们相信在实践中遇到问题、解决问题、反思问题，才是知识真正生根的方式。

在 CS2023 胜任力模型的视角下，真正的专业胜任力由三维深度咬合而成：

* **知识 (Knowledge)**：不靠死记硬背，而是作为系统决策与架构判断的基石（Know-Why）。
* **技能 (Skills)**：不只是写出代码片段，而是端到端的构建、调试、重构与交付力（Know-How）。
* **品行 (Dispositions)**：**人类工程师与 AI 的核心分水岭**——面对未知的排错韧性、对边界条件的工匠严谨、对 AI 生成物的审慎怀疑、以及在团队中的同理与责任担当（How to Act）。

换句话说：不要和 AI 竞争“解释世界”的能力——那是它擅长的。你要获得的是“改造世界”的三维胜任力——那是只有你才能做到的。

这门课的全部设计，都围绕这一个核心信念展开：

* 你不是来学习“关于软件”的。你是来**做软件**的。
* 你是来亲手实现一个算法，让它第一次在真实的计算机上跑起来——哪怕这个算法只是对教科书例题的一行改进，那也是你在这个世界上留下的一小行足迹。
* 你是来学会如何与“其他改造世界的人”一起工作——通过结对编程让队友看懂你的每一行代码，通过 Peer Review 对同伴的代码提出有意义的质疑，通过参与开源社区在全球协作的网络中占据一个小小的节点。
* 你是来学会**如何驾驭 AI 而非沦为它的传声筒**——具备审查 AI 代码缺陷的火眼金睛，并对系统的每一次发布负起工程师的主权责任。

这门课不保证你记住所有语法细节，但它承诺一件事：当你走出去的时候，你已经是一个能做事、能合作、能对着一行代码说“这是我写的（或我审查并重构的），我能解释它，我也能改进它”的人。

## 教学对象与五大现实挑战

授课对象是一群非常聪明但习惯截然不同的学生，教学落地面临五大现实挑战：

| 序号 | 挑战维度 | 现实痛点与挑战描述 |
| --- | --- | --- |
| 1 | **时空节点** | 2026 年的 CS 101——面对普及的 AI 编程助手与智能体（Agent），传统的“实现导向型”编程教学已无法适应当前的工程环境。 |
| 2 | **极化的起点能力** | 同在一个班级，有人已经是灵活调用 Cursor/Claude 的 Vibe Coding 熟手，有人却连命令行是什么都未曾听闻，计算机键盘盲打可能有问题，基础极度参差不齐。 |
| 3 | **“Mobile-First”的认知倒错** | 作为移动端原住民，学生习惯了 iOS/Android 无文件系统的 UI，对目录树、内存/硬盘、相对/绝对路径、环境变量缺乏直观印象，习惯把所有文件堆在桌面。 |
| 4 | **外部环境的噪音** | 网络上充斥着“AI 无所不能”、“代码已死”的言论，极大地冲击着大一新生的学习心态。 |
| 5 | **教学目标的落实** | 在课程既定的“培养扎实面向对象（OOP）思维与工程协作能力”目标下，如何引导学生克服对 AI 的盲目依赖、纠正不良开发习惯、塑造专业工程品行，成为教学设计的核心议题。 |

面对这五大挑战，我们的回答不是“讲得更清楚”，而是“让学生在真实的工程情境（Context）中做更真实的事”。

## 教学隐喻：“乱牌麻将”与软件工程的协同品行

一流大学的学生都是有各种各样的聪明才智，例如，一些聪明的学生在打麻将时，牌从不按花色和顺序排列，随手乱放，但他自己记性好、脑子快，依然能打得很好。对“单人打牌”来说，这完全不是问题；但用软件改变世界从来不是一个人的游戏，而是团队接力。

如果两个人合力打一手牌，你却把牌理得七零八落，队友就完全无法理解你的思路。同样，在软件工程中，文件随手扔桌面、不写接口定义、依赖 AI 随意生成未经审查的代码——这些本质上就是在“乱放麻将牌”。它们没有解决任何软件开发的本质困难（Essential Complexity），反而制造了大量人为的、琐碎的困难（Accidental Complexity），极大地消耗了团队的精力。

更要命的是，大学之前的学习几乎全是单打独斗，而大学之后，我们必须像真实社会一样，学会与同学建立既竞争又合作的“竞合”关系。我们的代码不仅要今天能跑，更要让同伴看得懂，明天能改、后天能维护——这种长期演进的协作模式，对大一新生而言，是一种全新的工程品行（Dispositions）与工作方式的挑战。

## 一个开篇的澄清：开源不是“以后的事”

在正式展开教学方案之前，我们需要先破除一个常见错觉：“开源”是极客的事，或者等我工作进大厂了才会接触。

事实是，2026 年的大一新生从入学第一天起，就已经生活在开源构建的世界里——你手机里的 Android（基于 Linux）、你写代码用的 VS Code（开源）、你运行程序的 Python 解释器（开源），甚至你可能会用到的 Arduino 开发板（开源硬件），全都来自开源社区。你不是“以后”才会接触开源，你此刻就在使用它。

而在这门课中，我们会更进一步——你不是在学习“关于”开源的知识，而是直接用开源的方式来完成这门课。课程资料放在 GitHub/Gitee 上，你通过提交 Issue 来报名和提问，通过发起 Pull Request 来交作业。这门课本身，就是你参与的第一个开源项目。

我们相信：**用开源的方式教开源，才是真正的 Dogfooding。**

## 一、 核心痛点与解决逻辑

针对上述挑战，我们不能靠口头劝导或机械禁令，而要通过 **“硬性工程约束（CI/CD）”、“命令行与文件系统基建（Missing Semester）”、“同侪协作机制（结对与 Review）” 与 “有趣且具挑战性的非罐头项目”** 五位一体来重构教学。

考虑到不同学校与专业新生的基础差异，课程在要求上不做“一刀切的全面精通”，而是设立阶梯式胜任力愿景：

> **核心胜任力愿景**：
> “把一个你用 AI 写（也可以自己写）的程序，关掉 AI 后在白板或纸面上讲清楚它为什么这么设计、内存里长什么样；出了基础 bug 能在提示或工具辅助下定位并修复；还能借助模板和命令行把编译环境跑起来。”

在 Missing Semester 与工程大作业等真实工程情境（Context）驱动下，这种胜任力具体拆解为三个维度的梯次融合：

* **知识维度 (Knowledge)**：掌握文件树拓扑与路径原理，初步理解面向对象（OOP）抽象、封装与契约设计，建立对程序内存分布与版本演化的基本概念。
* **技能维度 (Skills)**：熟练运用基础终端命令与 Git 工作流；在构建脚本（CMake）或脚手架模板辅助下完成工程编译；初步掌握代码调试与纸面推演，跑通 PR 提交与代码互审流程。
* **品行维度 (Dispositions)**：恪守规范自律（杜绝桌面死路径），对 AI 生成代码保持审慎怀疑，在团队结对与代码评审中展现同理心与开放心态。

**解决链路**：
移动端原住民与 AI 依赖的现状，需要通过 CLI 基建与头文件先行的训练来夯实基础；在此基础上，引入结对编程与 Peer Review 机制，培养协作习惯与工程品行；随后通过非罐头项目与 CI/CD 自动化构建进行实战检验；最终达成扎实的工程素养与面向对象（OOP）设计能力。

## 二、 破局 AI 依赖：扎实面向对象（OOP）功底与审慎品行

将考核重心从“程序运行成功”转移到“接口设计质量、抽象能力、底层原理理解与对生成代码的批判性审视”。

### 2.1 实施“头文件先行（Header-First）”契约防线

* **做法**：项目阶段一只允许编写 `.h` 头文件（定义类接口、成员变量访问控制、虚函数、封装关系），不允许写 `.cpp` 实现。
* **目的与胜任力要求**：
* **[K]** **初步理解**抽象屏障（Abstraction Barrier）、信息隐藏与类间职责划分。
* **[S]** 能看懂并初步设计基本的类接口契约（普通高校以补全/设计简单类为主，高阶班级要求独立定义抽象接口）。
* **[D] 契约精神与审慎思考**：强制学生在不依赖 AI 补全具体实现逻辑的情况下，先独立思考架构设计与契约边界，对团队接口负起责任。头文件通过评审后，方可进行实现。



### 2.2 引入“代码答辩（Code Defense）”与多维度能力检验

通过“口头设计决策 + 笔头执行细节 + 代码批判与优化 + 基础实现能力”四层防线，消除学生“代码跑通即万事大吉”的侥幸心理，倒逼其理解与审查每一行代码。

* **抽查答辩（可选）**：随机抽取 20% 的学生进行 3 分钟现场代码质询。问题聚焦于已学基础 OOP 概念，如：
* “这个类为什么要用 private 封装这些成员变量？如果不封装会有什么问题？”
* “解释一下这个构造函数在对象创建时做了什么？内存分配在栈还是堆？”
* “这段代码违反了哪条 OOP 设计原则？可以怎么改进？”
* “为什么这里要用 const 修饰成员函数？去掉 const 会有什么影响？”
* *评分准则*：回答不出者，作业得分打折；允许学生在质询过程中参考自己的代码或在白板上手绘简图辅助说明。
* *[D] 品行考察*：**求真与自信**——坦诚说明代码来源，清晰论证设计逻辑。


* **纸面追踪（Paper Tracing）测验（推荐）**：随堂发放纸质试卷，印有一段短小 C++ 程序（10-15 行，类似 LeetCode 简单题的核心逻辑，去除算法难度），要求学生仅通过人工推演，手写出程序执行完毕后的最终输出结果。例如：
```cpp
#include <iostream>
using namespace std;
int main() {
    int sum = 0;
    for (int i = 1; i <= 5; i++) {
        if (i % 2 == 0) {
            sum += i * 2;
        } else {
            sum += i;
        }
    }
    cout << "Sum = " << sum << endl;
    return 0;
}

```


学生只需在试卷上写出：`Sum = 15`。
* *考察目的*：考察基础语法、循环逻辑和条件判断的串联理解能力。纸面测试剥离了 IDE、AI 补全和编译器的辅助，迫使学生在无外部支持的环境下逐行推演代码语义，从根本上杜绝“代码跑通但脑子没跟上”的现象。由助教统一判卷，计入平时分。


* **纸面排错（Paper Debugging）与代码优化测验（可选）**：随堂发放纸质试卷，印有一段 30-50 行、功能正确但代码质量极低的 C++ 程序（变量命名混乱、逻辑重复、深层嵌套、魔数遍地、职责混杂）。试卷分为两页，分阶段发放：
* *第一页（20 分钟）——找茬*：通读代码，列出至少 5 个问题并标注类别（命名、重复、嵌套、魔数、职责、潜在内存泄漏等），简要解释原因。
* *第二页（25 分钟）——修复与优化*：收走第一页，发放同一段代码的纯净版，要求在纸面上直接修改（划掉重写、插入新行、重新组织），并在空白处写明修改理由。
* *评分依据*：问题发现质量（30%）+ 修复质量（30%）+ 优化程度（40%）。
* *[D] 品行考察*：**批判性思维与代码品味**——培养“判断什么是好代码，并有能力把烂代码变好”的专业追求。


* **限时手写 / 无网机房测验（推荐）**：在实验室关闭外网与 AI 插件，要求学生在 30 分钟内完成 1-2 道基础 LeetCode 题目（Easy 级别，如 *412. Fizz Buzz*、*2469. Convert the Temperature*、*1929. Concatenation of Array*、*2652. Sum Multiples*）。
* *考察目的*：检验学生在无 AI 辅助下独立写出可编译、能通过样例测试的基本功。“带键盘的纸面追踪”，证明自己脱离 AI 依然具备扎实的实现底座。

## 三、 弥合认知断层：从 Mobile-First 到工程基建与工匠自律

补齐大学理论课常忽略的“Missing Semester”工程基本功，建立起真实的“文件系统与路径”脑内图谱与工匠自律品行。

### 3.1 开学前两周：“Missing Semester”工程基建通关营

借鉴 MIT 开创的《The Missing Semester of Your CS Education》课程理念，前两周禁用一切图形化 IDE 的“拖拽式新建”，所有项目创建、目录切换、文件编译必须在终端（Shell/CMD）中完成。

为防止大一新生因“环境装不上”而在第一晚产生挫败感，教学设计采用结构化手段将“琐碎困难”降到最低，让学生精力聚焦在核心能力上：

* **第一周：文件系统与 Shell 基本功**
* *告别桌面——文件系统树与路径遍历*：使用 `tree` 打印整个用户目录，理解桌面在树形结构中的位置。练习 `mkdir -p` 一次性创建三级目录，用 `cd -` 快速跳转。
* *死路径红线*：提供脚本自动扫描提交的代码，若发现包含 `C:\Users` 或 `/home/xxx/Desktop` 等绝对路径模式，直接拒绝接收。
* *文件操作与通配符*：给定杂乱目录，使用一行 `mv *.h include/` 完成分类归档。
* *环境变量与 PATH 之谜*：通过 `which python` 与 `echo $PATH` 分析 Shell 寻址机制；模拟环境故障并限时诊断修复。
* *输入输出重定向与管道*：使用 `>`、`>>`、`2>&1` 处理输出；组合 `ps aux | grep code | wc -l` 统计进程；编写 `build.sh` 脚本，将编译输出同时显示在屏幕并保存到 `build.log`。
* *终端紧急编辑（Vim/Nano）*：掌握无 GUI 下的基础编辑指令（`i` 插入、`ESC`、`:wq` 保存、`:q!` 退出）。场景实操：SSH 连接远程服务器修复写错的 `CMakeLists.txt`。


* **第二周：版本控制与自动化构建**
* *Git 本地工作流*：将 Git 比作游戏“存档点”（`init`、`add`、`commit`、`log --oneline --graph`）。提交信息必须遵循 `<type>: <subject>` 规范（如 `feat: add player move`），否则 CI 拦截。
* *Git 远程协作与 PR 工作流*：Fork 教学骨架库 $\rightarrow$ Clone 本地 $\rightarrow$ 创建特性分支 $\rightarrow$ Push $\rightarrow$ 发起 PR。将第一周脚本整理成 `tools/` 目录并通过 PR 提交。
* *CMake 入门与外部构建*：解剖最小 `CMakeLists.txt`。基线要求能**初步理解其结构并照着模板修改**，在 `build/` 目录外执行 `cmake .. && make`，体验 Out-of-source 外部构建的纯净性。
* *包管理器与单元测试（选做/体验）*：演示 Google Test 单元测试框架，学有余力者可体验利用 FetchContent 进行依赖管理。
* *综合通关实战——“msc-project”*：目录结构规范（`include/`、`src/`、`tests/` 分离），支持 `make test`（或基础编译脚本），README 完备且至少包含 3 条规范 Commit。提交 GitHub 链接由自动化脚本拉取、构建、测试与评分。


* **教学支持与防挫败机制**：
* *“导航员”轮岗制*：高年级学长每日在 Discord/Slack 在线解答环境问题。
* *虚拟机镜像保底*：提供预装 Ubuntu、VS Code、Git、CMake、GCC/Clang 的虚拟机镜像，避免卡在安装环节。
* *看板追踪与“英雄贴”挑战*：GitHub Classroom 可视化追踪通关状态；每日发布 1-2 个加分附加题（如“一行命令找出大于 10MB 文件并排序”）。


* **[D] 长远价值与品行塑造**：
* 命令行不仅是当下的基建，更是为人机协同打底——2026 年的 AI 智能体（如 claude、cursor-agent、aider）大量以 CLI 形式存在。Shell 是人机协作的底层通用协议。
* 培养**工匠自律（Discipline & Rigor）**与**排障韧性（Resilience）**：面对黑底白字的错误日志不退缩，追求系统的可移植性（Portable）与整洁性。



### 3.2 建立硬性“自动化构建与零分红线”（CI/CD 机制）

* **标准化工程目录结构**：
```text
my_project/
├── CMakeLists.txt    # 自动化构建脚本
├── include/          # 存放 .h 头文件与接口契约
├── src/              # 存放 .cpp 实现文件
├── tests/            # 单元测试代码 (Google Test)
└── README.md         # 工程说明与架构文档

```


* **零分红线**：不接受压缩包或桌面截图提交，统一通过 Git 仓库提交。CI 自动拉取构建，凡无法一键编译、测试用例不通过、或代码中残留桌面绝对路径者，直接判定为 0 分。

## 四、 引入同侪机制：从两人结对到全球开源协作（Dogfooding）

利用优秀本科生重视同侪评价（Peer Recognition）的心理，将“不规范代码”转化为“对队友的直接困扰”，让不良习惯无处遁形。

### 4.1 动态角色结对编程（Pair Programming）

两人一组，采用“驾驶员（Driver）与导航员（Navigator）”模式，定期轮换角色：

| 角色 | 核心职责 | 胜任力与品行要求 |
| --- | --- | --- |
| **驾驶员 (Driver)** | 负责键盘输入、语法实现与即时代码编写。 | 专注局部逻辑实现，主动向导航员解释自己的编码意图。 |
| **导航员 (Navigator)** | 负责实时审计、边界提问与架构长远设计。 | **审慎质疑**：当驾驶员盲目复制 AI 代码时现场质询；当文件随手放桌面时即刻纠偏。 |

### 4.2 Pull Request 与代码互审（Peer Review）

* **做法**：代码合并至主分支前，必须经由结对队友的 Code Review 并 Approve。
* **规约**：若代码包含绝对路径、缺乏头文件封装、没有配套测试或 Commit 信息混乱，队友有权且必须 Reject。
* **[D] 建设性品行**：Review 评语必须客观具体（采用 `Suggestion:` 规范，对事不对人）；被审者需具备接纳反馈的**开放心态（Openness）**。

### 4.3 延伸至开源世界：用开源的方式教开源（Dogfooding）

* **理念**：开源已经构成了现代数字世界的底座（Linux、VS Code、Python、RISC-V 等）。2026 年的大一新生不仅是开源的“消费者”，更是未来的“贡献者”。
* **课程即仓库 (Course as Repository)**：教学大纲、作业说明与示例全部开源托管于 GitHub/Gitee。学生通过 Issue 报名提问，通过 Fork + PR 提交作业。
* **身份准备与启蒙**：指导激活 GitHub Student Developer Pack；带领学生精读顶级开源项目的 `README.md` 与 `CONTRIBUTING.md`。
* **选做加分挑战**：鼓励学有余力的同学向外部真实开源项目提交标记为 `good-first-issue` 的 PR（如补充单测、修复文档），纳为附加分。
* **Dogfooding 价值**：用开源的真实流程完成课程本身，让“让别人看懂代码”的协作素养直接在真实生态中生根。

## 五、 拒绝“罐头项目”：设计有挑战、高趣味的实战大作业

废除在 AI 训练集中有海量现成代码的“贪吃蛇”、“图书管理系统”等罐头项目。项目设计遵循 **“框架给定，插件自定义；解决实际小痛点、强约束、高扩展、自带同侪竞技性”** 原则。

### 5.1 项目一：面向对象智能体竞技场（Bot Battle Arena）

* **设计**：教学组提供开源坦克大战或回合制卡牌游戏底座框架。学生利用 OOP 思想（继承、多态、策略模式、状态模式）编写属于自己的 Bot 决策逻辑。
* **亮点**：不写渲染逻辑，只写领域抽象；AI 无法一键生成胜率最高的对抗逻辑。每周由 CI/CD 自动举办全班 Bot 联赛，极大激发工程好胜心。

### 5.2 项目二：Terminal Rogue-like 迷宫引擎

* **设计**：结合 CLI 终端训练，设计基于字符画的终端游戏引擎。
* **亮点**：强约束接口——玩家（Player）、怪物（Monster）、道具（Item）必须继承自同一个 `GameObject` 基类并实现纯虚函数；地图加载必须通过相对路径读取，严禁硬编码。

### 5.3 项目三：“代码考古”与 OOP 重构拯救计划

* **设计**：给定一份可运行但写在单个文件、充满全局变量与内存泄漏的旧 C 语言“烂代码”。要求学生重构为标准的 C++ 多文件工程，并用 AddressSanitizer/Valgrind 证明零泄漏。
* **亮点**：训练代码阅读与架构重构能力，体验从无序到有序的工程价值。

## 六、 AI 时代的工程伦理与透明度契约

CS2023 高度强调工程师的职业伦理与社会责任。课程设立显式的 **AI 透明度与责任契约（AI Transparency Contract）**：

1. **全面拥抱但公开透明**：允许合理使用 AI，但必须在每次 PR 描述中提交 **AI Usage Disclosure**：
* *哪些类或算法模块借助了 AI 辅助生成？*
* *给 AI 的 Prompt 提示词是什么？*
* *AI 初稿存在哪些性能、内存或边界缺陷？你是如何审查并重构它的？*


2. **责任归属与主权意识**：**AI 可以是你的“副驾驶”（Copilot），但人类工程师永远对每一次系统发布、数据安全与程序崩溃承担最终法律与工程责任。**

## 七、 基于 CS2023 胜任力模型的课程考核矩阵

将知识、技能与品行转化为梯次可观测、可度量的量规（Rubric）：

| 考核模块 | 权重 | 知识维度 (Knowledge) | 技能维度 (Skills) | 品行显式观测点 (Dispositions) |
| --- | --- | --- | --- | --- |
| **Missing Semester 与工程基建** | 20% | 掌握文件树拓扑，初步理解环境变量与构建脚本（CMake）基本机制。 | 熟练使用常用 Shell 管道与 Git 命令；能依据模板修改并成功执行工程编译。 | **工匠自律与规范**：提交记录中 0 绝对路径；Commit 严格遵循 Conventional Commits 规范。 |
| **OOP 架构与接口设计** | 30% | 初步理解封装、抽象屏障、单一职责与基础多态机制。 | 能看懂并编写规范的 `.h` 头文件；初步掌握编写单元测试验证核心逻辑。 | **架构审慎与自律**：不写随意的面条代码，注重接口边界，主动控制技术债务。 |
| **结对协作与开源实践** | 20% | 初步理解 PR 协作流程、分支策略与开源 Code of Conduct 规范。 | 规范发起原子化 PR；能对照 Checklist 指出同伴代码中的格式与逻辑缺陷。 | **同理心与建设性**：Review 评语具有建设性（对事不对人）；积极响应同伴修改建议。 |
| **代码答辩与原理质询** | 30% | 纸面追踪与排错正确；初步理解程序执行流与基础内存模型（栈与堆概念）。 | 脱离 IDE 与网络，能在白板或纸面上推演简单代码执行过程并回答设计决策。 | **求真诚信与责任感**：坦诚界定 AI 辅助与自研边界；清晰解释自己的设计逻辑。 |

## 结语

> **“规范的目录是工程的骨架，头文件是设计的思想，结对与 Review 是工程文化的土壤。”**

通过“乱牌麻将”的比喻建立沟通共识，用命令行与 CMake 重塑文件系统直觉，用头文件先行构筑架构防线，用同侪 Review 滋养工程文化，用防 AI 罐头的竞技项目激发激情，用开源 Dogfooding 链接真实生态——

**知识决定你知道去向何方，技能决定你能否亲手抵达，而工程品行，决定了你和你的团队能在未来的风浪中走多远。**

## 推荐阅读

在课程教学之外，我们建议学生（及教学团队）阅读以下书籍，作为对数字世界底层逻辑的“认知筑基”：

| 项目 | 内容 |
| --- | --- |
| **书名** | **《世界是数字的》**（英文原名：*D is for Digital*） |
| **作者** | **Brian W. Kernighan**（普林斯顿大学计算机科学教授，*The C Programming Language* 合著者，“Unix 传奇”先驱之一） |
| **定位** | 面向非计算机专业学生及大众读者的计算机科学通识读本，源于作者在普林斯顿大学开设的经典名课“Computers in Our World”。 |
| **内容框架** | 全书分为三大模块：**硬件 (Hardware)**——比特与字节、CPU 与存储层次；**软件 (Software)**——算法、编程语言与操作系统；**通信 (Communications)**——网络与互联网架构。后续版本补充了数据、隐私、安全与人工智能章节。 |
| **与本课程理念的关联** | 本书不追求教你成为码农，而是培养**“对数字世界有清醒认知的创造者”**。它所强调的“理解计算机系统底层如何运转”的思维方式，与我们在 CS 101 中倡导的“不盲目依赖 AI、理解每一行代码背后的原理、用软件改造世界”一脉相承。建议大一新生将其作为开学第一课的筑基读物。 |
