# AI 时代的软件第一门课怎么教

> **注：** 这是一个建议初稿，针对的是理工科大一的第一门软件课程（CS 101），未必适合所有学校和专业，欢迎点评讨论。

---

## 序言：2026 级理工科本科生的五大真实课堂挑战

作为 2026 年大学一年级理工科的第一门编程课（CS 101）教学团队，我们面临的课堂环境已经发生了深刻的变化。授课对象是一群非常聪明但习惯截然不同的学生，教学落地面临五大现实挑战：

| 序号 | 挑战 | 描述 |
|:---:|------|------|
| 1 | **时空节点** | 2026 年的 CS 101——面对普及的 AI 编程助手与智能体，传统的"实现导向型"编程教学已无法适应当前的工程环境。 |
| 2 | **极化的起点能力** | 同在一个班级，有人已经是灵活调用 Cursor/Claude 的 Vibe Coding 熟手，有人却连命令行是什么都未曾听闻，计算机键盘盲打可能有问题，基础极度参差不齐。 |
| 3 | **"Mobile-First"的认知倒错** | 作为移动端原住民，学生习惯了 iOS/Android 无文件系统的 UI，对目录树、内存/硬盘、相对/绝对路径、环境变量缺乏直观印象，习惯把所有文件堆在桌面。 |
| 4 | **外部环境的噪音** | 网络上充斥着"AI 无所不能"、"代码已死"的言论，极大地冲击着大一新生的学习心态。 |
| 5 | **教学目标的落实** | 在课程既定的"培养扎实面向对象（OOP）思维与工程协作能力"目标下，如何引导学生克服对 AI 的盲目依赖、纠正不良开发习惯，成为教学设计的核心议题。 |

### 教学隐喻："乱牌麻将"与软件工程

很多极聪明的学生在打麻将时，牌从不按花色和顺序排列，随手乱放，但他自己记性好、脑子快，依然能打得很好。对"单人打牌"来说，这完全不是问题；但软件工程从来不是一个人的游戏，而是团队接力。

如果两个人合力打一手牌，你却把牌理得七零八落，队友就完全无法理解你的思路。同样，在软件工程中，文件随手扔桌面、不写接口定义、依赖 AI 随意生成代码——这些本质上就是在"乱放麻将牌"。它们没有解决任何**软件开发的本质困难（Essential Complexity）**，反而制造了大量**人为的、琐碎的困难（Accidental Complexity）**，极大地消耗了团队的精力。

更要命的是，大学之前的学习几乎全是单打独斗，而大学之后，我们必须像真实社会一样，学会与同学建立**既竞争又合作的"竞合"关系**。我们的代码不仅要今天能跑，更要让同伴看得懂，明天能改、后天能维护——这种长期演进的协作模式，对大一新生而言，是一种全新的心态挑战。

---

### 一个开篇的澄清：开源不是"以后的事"

在正式展开教学方案之前，我们需要先破除一个常见错觉：**"开源"是极客的事，或者等我工作进大厂了才会接触。**

事实是，2026 年的大一新生从入学第一天起，就已经生活在开源构建的世界里——你手机里的 Android（基于 Linux）、你写代码用的 VS Code（开源）、你运行程序的 Python 解释器（开源），甚至你可能会用到的 Arduino 开发板（开源硬件），全都来自开源社区。**你不是"以后"才会接触开源，你此刻就在使用它。**

而在这门课中，我们会更进一步——**你不是在学习"关于"开源的知识，而是直接用开源的方式来完成这门课**。课程资料放在 GitHub/Gitee 上，你通过提交 Issue 来报名和提问，通过发起 Pull Request 来交作业。这门课本身，就是你参与的第一个开源项目。

> 我们相信：**用开源的方式教开源，才是真正的 Dogfooding。**

## 一、核心痛点与解决逻辑

针对上述挑战，我们不能靠口头劝导或机械禁令，而要通过 **"硬性工程约束（CI/CD）"**、**"命令行与文件系统基建（Missing Semester）"**、**"同侪协作机制（结对与 Review）"** 与 **"有趣且具挑战性的非罐头项目"** 五位一体来重构教学。

**解决链路：**

移动端原住民与 AI 依赖的现状，需要通过 CLI 基建与头文件先行的训练来夯实基础；在此基础上，引入结对编程与 Peer Review 机制，培养协作习惯；随后通过非罐头项目与 CI/CD 自动化构建进行实战检验；最终达成基本的工程素养与简单的 OOP 设计能力。

## 二、破局 AI 依赖：扎实面向对象（OOP）功底

将考核重心从"程序运行成功"转移到"接口设计质量、抽象能力与底层原理理解"。

### 2.1 实施"头文件先行（Header-First）"防线

**做法：** 项目阶段一只允许编写 `.h` 头文件（定义类接口、成员变量访问控制、虚函数、封装关系），不允许写 `.cpp` 实现。

**目的：** 强制学生在不依赖 AI 补全具体实现逻辑的情况下，先思考类与类之间的"职责划分"与"契约设计"。头文件通过评审后，方可进行实现。

### 2.2 引入"代码答辩（Code Defense）"与多维度能力检验

**做法：**

- **抽查答辩：** 随机抽取 20% 的学生进行 3 分钟现场代码质询。问题聚焦于**课程已讲授的基础 OOP 概念**，例如：
  - "这个类为什么要用 `private` 封装这些成员变量？如果不封装会有什么问题？"
  - "解释一下这个构造函数在对象创建时做了什么？"
  - "这段代码违反了哪条 OOP 设计原则？可以怎么改进？"
  - "为什么这里要用 `const` 修饰成员函数？去掉 `const` 会有什么影响？"
- 回答不出者，作业得分打折；但允许学生在质询过程中**参考自己的代码**或**手绘简图**辅助说明。

- **纸面追踪（Paper Tracing）测验：** 随堂发放纸质试卷，上面印有一段短小的 C++ 程序（10-15 行，风格类似 LeetCode 简单题的核心逻辑，但去除算法难度），要求学生**仅通过人工推演，手写出程序执行完毕后的最终输出结果**。例如：

```cpp
#include <iostream>
using namespace std;

int main() {
    int sum = 0;
    for (int i = 1; i <= 5; i++) {
        if (i % 2 == 0) {
            sum += i * 2;
        } else {
            sum += i;
        }
    }
    cout << "Sum = " << sum << endl;
    return 0;
}
```

**学生只需在试卷上写出：** `Sum = 15`

此类题目考察的是**基础语法、循环逻辑和条件判断**的串联理解能力，而非算法技巧。代码不含类继承、虚函数、动态内存分配等进阶概念，确保大一新生在掌握基本控制结构后即可作答。AI 可以帮学生生成代码，但无法代替他们在考场上逐行推演执行过程。

纸面测试剥离了 IDE、AI 补全和编译器的辅助，迫使学生在**无外部支持**的环境下逐行推演代码语义，从根本上杜绝"代码跑通但脑子没跟上"的现象。判卷由助教统一完成，成绩计入平时分。

- **限时手写 / 无网机房测验：** 在实验室关闭外网/AI 插件，要求学生在 30 分钟内完成 1-2 道从 LeetCode 抽取的题目（难度限定在 **Easy ~ Medium 中不涉及复杂算法**的类型，如数组遍历、字符串处理、简单数学逻辑）。例如：
  - [LeetCode 412. Fizz Buzz](https://leetcode.com/problems/fizz-buzz/) —— 循环与条件判断
  - [LeetCode 2469. Convert the Temperature](https://leetcode.com/problems/convert-the-temperature/) —— 简单数学计算
  - [LeetCode 1929. Concatenation of Array](https://leetcode.com/problems/concatenation-of-array/) —— 数组基本操作
  - [LeetCode 2652. Sum Multiples](https://leetcode.com/problems/sum-multiples/) —— 循环累加与取模

这类题目不涉及贪心、动态规划、图论等算法知识，但足以检验学生**在无 AI 辅助下独立写出可编译、能通过样例测试的代码**的基本功。它本质上就是"带键盘的纸面追踪"——难度依然友好，但测试维度从"读懂代码"扩展到了"写出代码"。因为 LeetCode 题目广泛存在于 AI 训练集中，学生无法以"AI 能写"为由回避考核——**正是要他们证明自己能写**。

**目的：** 通过"口头设计决策 + 笔头执行细节 + 基础实现能力"三层防线，消除学生"代码跑通即万事大吉"的侥幸心理，倒逼其理解 AI 生成的每一行代码。

## 三、弥合认知断层：从 Mobile-First 到 PC 操作系统与目录结构

补齐大学理论课常忽略的"Missing Semester"工程基本功，强迫学生建立起真实的"文件系统与路径"脑内图谱。

### 3.1 开学前两周："Missing Semester"工程基建通关营

**做法：** 借鉴 MIT 开创的《The Missing Semester of Your CS Education》课程理念——该课程旨在填补大学计算机科学理论教育与实际工业开发所需工具链之间的巨大鸿沟，涵盖 Shell、Git、调试、构建系统等被传统课堂忽视却至关重要的实战技能——前两周禁用一切图形化 IDE 的"拖拽式新建"，所有项目创建、目录切换、文件编译必须在终端（Shell/CMD）中完成。

但我们也必须正视一个真实存在的风险：**"从安装到放弃"**。对许多大一新生而言，配置开发环境——安装编译器、设置环境变量、让 Git 与 SSH 密钥配对、让 CMake 找到正确的库路径——本身就是一堵高高的墙。一句陌生的报错信息、一个缺失的依赖包，就足以让一个满怀好奇的学生在第一个晚上彻底失去信心。

这些困难本质上都属于 **"人为的、琐碎的困难（Accidental Complexity）"**，它们与计算机科学的核心思想无关，却真实地阻碍了学生进入后续的学习。如果我们不主动干预，那些原本对编程充满热情的学生，可能会因为"装不上"而自我怀疑，甚至在正式开始写代码之前就已经放弃了。

因此，我们的教学设计必须做到：**用结构化手段将"琐碎困难"降到最低，让学生的认知精力聚焦在"本质困难"上**——而不是让工具链本身成为第一道不可逾越的门槛。具体措施如下：

**两周通关营详细日程：**

**第一周：文件系统与 Shell 基本功**

- **Day 1：告别桌面——文件系统树与路径遍历**
  - 让学生用 `tree` 命令打印整个用户目录，回答："你的桌面（Desktop）在树形结构中处于什么位置？它的父节点是谁？"
  - 作业：使用 `mkdir -p` 一次性创建三级目录 `project/include/utils`，并用 `cd -` 在最近两个目录间跳转。
  - 死路径红线：教学组提供脚本，扫描提交的代码中是否包含 `C:\Users` 或 `/home/xxx/Desktop` 等绝对路径模式，发现则拒绝接收。

- **Day 2：文件操作与通配符魔法**
  - 实战：给定混有 `.h`、`.cpp`、`.o`、`.tmp` 文件的杂乱目录，用一行 `mv *.h include/` 等命令完成分类归档。
  - 使用 `rename` 命令将 `Test_*.cpp` 批量重命名为 `unittest_*.cpp`。

- **Day 3：环境变量与 PATH 之谜**
  - 实验：通过 `which python` 与 `echo $PATH` 分析 Shell 如何找到命令。
  - 模拟故障：安装"假想工具"但故意不加入 PATH，让学生诊断并修复。

- **Day 4：输入输出重定向与管道**
  - 核心训练：使用 `>`、`>>`、`2>&1` 处理标准输出和错误输出；组合 `ps aux | grep code | wc -l` 统计进程数。
  - 工程应用：编写 `build.sh` 脚本，将编译输出同时显示屏幕并保存到 `build.log`（使用 `tee` 命令）。

- **Day 5：终端紧急编辑（Vim/Nano）**
  - 目标：不成为高手，但必须掌握在无图形界面服务器下修改配置文件的基本操作（`i` 插入、`ESC`、`:wq` 保存、`:q!` 退出）。
  - 场景考试：SSH 模拟连接远程服务器，发现 `CMakeLists.txt` 写错库名，限时 3 分钟用终端编辑器修复。

**第二周：版本控制与自动化构建**

- **Day 6：Git 本地工作流**
  - 概念破冰：将 Git 比作游戏"存档点"（`init`、`add`、`commit`、`log --oneline --graph`）。
  - 强制规范：提交信息必须遵循 `<type>: <subject>` 格式（如 `feat: add player move`），否则 CI 不通过。

- **Day 7：Git 远程协作与 PR 工作流**
  - 实操：Fork 教学组提供的"空项目骨架" → Clone 到本地 → 创建特性分支 → 修改后 Push → 发起 Pull Request。
  - 产出：将第一周所有 Shell 练习脚本整理成 `tools/` 目录，通过 PR 提交。

- **Day 8：CMake 入门**
  - 核心认知：CMake 是"编译器的生成器"，而非编译器本身。
  - 最小 `CMakeLists.txt` 解剖（含 `cmake_minimum_required`、`project`、`set`、`include_directories`、`add_executable`）。
  - 实践：在 `build/` 目录外执行 `cmake ..` 与 `make`，理解"外部构建（Out-of-source build）"的好处。

- **Day 9：包管理器与单元测试框架**
  - 场景：给项目引入 Google Test。演示系统级安装（`apt-get`）与项目级自动下载（`FetchContent`）。
  - 任务：为第一周的"统计 TODO 行数"脚本编写单元测试。

- **Day 10：综合实战——"Missing Semester 通关项目"**
  - 要求：项目名 `msc-project`，目录结构完全符合 `include/`、`src/`、`tests/` 分离；CMake 配置支持 `make test`；`README.md` 说明清晰；至少 3 条有意义 commit。
  - 验收：教学组提供自动化检查脚本，学生提交 GitHub 链接，脚本自动克隆、构建、运行测试并评分。

**强化练习贯穿两周：**

- 使用 `cd` / `ls` / `mkdir` / `tree` 等命令进行文件查找与管理。
- 将工程概念与数据结构课打通："目录就是一棵树（Tree Node），路径就是从根节点到目标节点的路径（Path Walk）"。
- 搞懂绝对路径与相对路径的区别（禁止出现类似 `C:\Users\...\Desktop\...` 的死路径）。

**教学支持与防挫败机制：**

- **"导航员"轮岗制**：由高年级学生或已掌握技能的同学每日值班，在 Discord/Slack 实时解答环境配置问题。
- **虚拟机镜像**：提供预装 Ubuntu、VS Code、Git、CMake、GCC/Clang 的 VirtualBox/VMware 镜像，避免"软件装不上"卡关。
- **进度追踪看板**：利用 GitHub Classroom 可视化每位学生的通关状态，连续两天落后自动发送提醒邮件。
- **"英雄贴"挑战**：每日 1-2 个附加题（如"用一行 Shell 命令找出所有大于 10MB 的文件并排序"），完成者获平时分加分。

**长远价值：**

掌握命令行不仅是当下的工程基建要求，更是为后续与 AI Agent 深度协作打下基础——2026 年的开发环境中，AI 编程助手与智能体越来越多地以命令行工具形态存在（如 `claude`、`cursor-agent`、`aider` 等），工程师通过 Shell 与这些 Agent 进行交互、传递上下文、执行自动化任务。**如果学生连目录切换和路径指代都不熟练，就不可能高效地指挥 AI Agent 工作。** 命令行不是要被淘汰的"古董界面"，而是人机协作最底层的通用协议接口。

### 3.2 建立硬性"自动化构建与零分红线"（CI/CD 机制）

**做法：** 引入标准工程目录结构，要求必须通过 Git 提交作业，并用 CMake 进行编译。

```
my_project/
├── CMakeLists.txt    # 自动化构建脚本
├── include/          # 存放 .h 头文件
├── src/              # 存放 .cpp 实现文件
├── tests/            # 单元测试
└── README.md         # 工程说明
```

**红线规定：** 不接受压缩包或桌面截图提交。统一提交到 GitHub/GitLab 仓库。运行自动测试脚本，如果无法通过 CMake 一键编译，或者路径依赖桌面，直接判定为 **0 分**。

## 四、引入同侪机制（Peer Accountability）：从两人结对到全球协作

利用优秀本科生重视同侪评价（Peer Recognition）的心理，将"不规范代码"转化为"对队友的直接困扰"，让 bad practice 无处遁形。同时，我们需要意识到：**课堂内的两人结对，只是全球开源协作模式的微缩版**。

### 4.1 动态角色结对编程（Pair Programming）

**做法：** 两人一组，采用"驾驶员（Driver）与导航员（Navigator）"模式，且必须定期交换角色。

| 角色 | 职责 |
|------|------|
| **驾驶员（Driver）** | 负责键盘输入与代码编写 |
| **导航员（Navigator）** | 负责实时审计、提问与思考长远设计。当驾驶员盲目复制 AI 代码时，导航员必须现场质询；当驾驶员把文件保存在桌面时，导航员需要纠正 |

### 4.2 Pull Request 与代码互审（Peer Review）

**做法：** 代码合并至主分支前，必须经由结对队友的 Code Review 并 Approve。

**规范：** 若代码中包含桌面绝对路径、缺乏头文件封装、或提交日志混乱，队友有权且应该 Reject 该合并请求。

**效果：** 让坏习惯直接导致"队友无法 Build"，形成同侪压力，让坏习惯在团队内部被消化（如同"乱打麻将牌"会让队友直接拒绝合力打牌）。

### 4.3 延伸至开源世界：用开源的方式教开源（Dogfooding）

当学生熟练掌握了课堂内的 PR 与 Review 流程后，需要认识到：**这套流程正是全球数百万开源开发者日常协作的标准方式**——而这套协作方式，离他们并不遥远。

**一个需要打破的认知误区：**

很多学生（甚至部分老师）会认为，"开源"是极客的事情，或者"等我工作进入大厂了才会接触"。但实际上，开源已经无处不在——**不只是软件，还有硬件**。RISC-V 开源芯片指令集正在重塑半导体行业；Arduino 和 Raspberry Pi 的开源硬件生态已经成为全球创客和工程教育的基础设施；开源科学工具（如 Jupyter、QGIS）正在改变研究人员的协作方式。2026 年的大一新生，从入学第一天起，就已经生活在开源构建的世界里。

**为何要在 CS 101 中让学生接触开源？**

一个基本事实是：**开源软件已经构成了现代数字世界的底座**。无论是 Android（基于 Linux）、VS Code，还是学生日常依赖的 Python 解释器、Git 工具，背后都有开源项目在驱动。截至 2024 年底，我国活跃开源项目已超 300 万个，活跃开发者达 227 万人。对于 2026 年入学的新生而言，他们不只是开源代码的"消费者"，更有机会也理应成为"贡献者"。

更关键的是，开源社区正是课程中强调的"竞合"关系的最真实体现——**全球无数开发者，在同一个仓库里既竞争（谁的代码更优雅、更快）又合作（共同维护一个项目）**，这恰好呼应了序言中提到的"心态挑战"。

**课程中的开源实践：Dogfooding —— 用开源的方式教开源**

我们相信：**如果课程本身不跑在开源工作流上，却大谈开源的重要性，这本身就是一种言行不一。** 因此，CS 101 的开源教学不只是一系列宣讲，而是将课程运作本身嵌入开源生态——**让学生从第一天起就生活在开源之中，而不是学习"关于"开源的知识。**

- **课程即仓库（Course as Repository）**：将课程大纲、作业说明、参考资料、代码示例全部托管在 GitHub 或 Gitee 的公开仓库中。**课程的所有更新通过 Git 发布**，学生通过 **Watch/Star** 仓库接收通知，通过 **Fork + Clone** 获取资料，通过 **提交 Issue** 来提问、报名项目、反馈问题。这门课本身就是学生参与的第一个"开源项目"。

- **作业即 Pull Request**：学生的每一次作业提交，都是一次完整的 PR 流程——Fork 仓库 → 创建分支 → 提交代码 → 发起 PR → 等待 Review → 合并或返工。这个过程与真实开源贡献**完全一致**。助教和队友的 Review 意见就是最直接的"社区反馈"。

- **身份准备**：指导学生注册 GitHub 账号，申请 **GitHub Student Developer Pack**（仅需 `.edu` 邮箱即可获得超 100 种免费开发工具）。让学生知道，他们作为大学生，已经拥有了开启开源之门的数字通行证。

- **意识启蒙**：选择 1-2 个学生可能已经在使用的开源项目（如 VS Code、Python 本身，或 Arduino 硬件库），带领学生快速浏览其 `README`、`CONTRIBUTING` 指南和 `Issue` 列表，让学生意识到：**他们每天使用的工具，其协作方式与他们提交作业的方式一模一样。**

- **选做加分挑战**：鼓励学有余力的学生尝试解决某个开源项目标记为 `good-first-issue` 的 Issue（如修正文档、补充单元测试），将此类外部贡献纳入课程的附加分体系。

通过以上设计，我们希望传递一个清晰的信号：**开源不是遥不可及的极客行为，也不是"工作以后才需要了解"的东西。** 它是软件（以及越来越多硬件）世界的通用语言和协作方式。学生在课堂 Pair Programming 中养成的"让队友看懂代码"的习惯，正是未来参与全球开源协作的底层素养。而课程本身的运作方式——从提交 Issue 报名到通过 PR 交作业——就是他们实践这一理念的第一个真实项目。**这就是 Dogfooding：用开源的方式，学会开源。**

## 五、拒绝"罐头项目"：设计有挑战、高趣味的大作业

废除"标准贪吃蛇"、"简单化图书管理系统"等在 AI 训练集中有海量模板的"罐头项目（Canned Projects）"。题目设计遵循 **"框架给定，插件自定义；解决一个实际小痛点、强约束、高扩展、自带同侪竞技性"** 原则。

### 5.1 项目一：面向对象智能体竞技场（Bot Battle Arena）

**设计：** 教学组提供一个开源的坦克大战或回合制卡牌游戏底座框架。学生需要利用 OOP 思想（继承、多态、策略模式、状态模式）编写属于自己的 Bot 逻辑接口。

**亮点：** 学生不写渲染逻辑，只写领域抽象。AI 无法一次性直接生成对抗逻辑；课程安排每周 CI/CD 自动举办 Bot 联赛，极大激发学生的工程好胜心。

### 5.2 项目二：Terminal Rogue-like 迷宫引擎

**设计：** 结合 CLI 终端训练，要求学生设计一个基于终端字符画的 Rogue-like 游戏引擎。

**亮点：** 强约束接口——玩家（Player）、怪物（Monster）、道具（Item）必须继承自同一个 `GameObject` 基类，并实现纯虚函数；地图加载必须通过相对路径读取文件，严禁硬编码。

### 5.3 项目三："代码考古"与 OOP 重构拯救计划

**设计：** 给定一份能够运行但完全写在一个文件中、充满全局变量与内存泄漏的 C 语言"烂代码"。要求学生用 OOP 设计原则重构为标准的 C++ 多文件工程，并用 Valgrind/Sanitizer 证明无泄露。

**亮点：** 训练学生的"代码阅读"与"架构整理"能力，直观体验从无序到有序的工程价值。

## 六、课程考核矩阵（推荐权重）

| 考核模块 | 权重 | 评分标准与规约 |
|----------|:----:|----------------|
| **Missing Semester 与 CI 构建** | 20% | Shell 命令操作、`include/`/`src/` 目录分离，CMake 一键编译无警告，Git Commit 规范 |
| **OOP 接口与设计** | 30% | 头文件设计合理性（封装性、继承抽象、接口隔离） |
| **结对协作与 Peer Review** | 20% | Git PR 互审记录、结对分工说明及同侪评价 |
| **代码答辩与原理质询** | 30% | 现场解释类设计逻辑、纸面追踪测验（手写代码输出与变量跟踪），确保真正掌握底座 |

## 七、总结

> **"规范的目录是工程的骨架，头文件是设计的思想，结对 Review 是工程文化的土壤。"**

通过"乱牌麻将"的比喻建立沟通共识，用命令行与 CMake 重塑文件系统直觉，用头文件与自动化 CI 强制工程骨架，用同侪 Review 滋养工程文化，用防 AI 罐头的竞技项目激发激情——这套方案旨在帮助 2026 级的大一新生迅速跨越习惯断层，成长为具备专业素养的软件工程师。而将课程本身跑在开源工作流上，则是这一切的"元实践"——用真实的方式，教真实的能力。

## 推荐阅读

在课程教学之外，我们建议学生（及教学团队）阅读以下书籍，作为对数字世界底层逻辑的"认知筑基"：

| 项目 | 内容 |
|------|------|
| **书名** | *D is for Digital*（中文版译名《世界是数字的》） |
| **作者** | Brian W. Kernighan（普林斯顿大学计算机科学教授，*The C Programming Language* 合著者） |
| **定位** | 面向非计算机专业学生及大众读者的计算机科学通识读本，源于作者在普林斯顿大学开设的课程"Computers in Our World" |
| **内容框架** | 全书分为三大模块：**硬件（Hardware）**——比特与字节、CPU 工作原理；**软件（Software）**——算法与编程语言；**通信（Communications）**——网络与互联网。后续版本补充了数据、隐私、安全、人工智能与机器学习等章节 |
| **与课程理念的关联** | 本书不追求培养程序员，而是培养"对数字世界有清醒认知的公民"。它所强调的"理解计算机系统如何工作"的思维方式，与我们在 CS 101 中倡导的"不盲目依赖 AI、理解每一行代码背后的原理"一脉相承。建议大一新生将本书作为课外拓展阅读，帮助建立对计算机科学的整体认知框架 |

## 附录：方案核心理念一览

- ✅ **不是禁止 AI**，而是让学生具备质疑 AI 生成代码的能力
- ✅ **不是死记硬背**，而是通过工程约束倒逼理解
- ✅ **不是单打独斗**，而是通过同侪机制培养团队意识
- ✅ **不是罐头项目**，而是有竞技性、有挑战的真实工程体验
- ✅ **不是宣讲开源**，而是用开源的方式上完整门课（Dogfooding）
