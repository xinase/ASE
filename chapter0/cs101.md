# AI 时代的软件第一门课怎么教

## 序言：2026 级本科生的五大真实课堂挑战

作为 2026 年大学一年级的第一门编程课（CS 101）教学团队，我们面临的课堂环境已经发生了深刻的变化。授课对象是一群非常聪明但习惯截然不同的学生，教学落地面临五大现实挑战：

| 序号 | 挑战 | 描述 |
|:---:|------|------|
| 1 | **时空节点** | 2026 年的 CS 101——面对普及的 AI 编程助手与智能体，传统的"实现导向型"编程教学已无法适应当前的工程环境。 |
| 2 | **极化的起点能力** | 同在一个班级，有人已经是灵活调用 Cursor/Claude 的 Vibe Coding 熟手，有人却连命令行是什么都未曾听闻，基础极度参差不齐。 |
| 3 | **"Mobile-First"的认知倒错** | 作为移动端原住民，学生习惯了 iOS/Android 无文件系统的 UI，对目录树、相对/绝对路径、环境变量缺乏直观印象，习惯把所有文件堆在桌面。 |
| 4 | **外部环境的噪音** | 网络上充斥着"AI 无所不能"、"代码已死"的言论，极大地冲击着大一新生的学习心态。 |
| 5 | **教学目标的落实** | 在课程既定的"培养扎实面向对象（OOP）思维与工程协作能力"目标下，如何引导学生克服对 AI 的盲目依赖、纠正不良开发习惯，成为教学设计的核心议题。 |

---

### 教学隐喻："乱牌麻将"与软件工程

很多极聪明的学生在打麻将时，牌从不按花色和顺序排列，随手乱放，但他自己记性好、脑子快，依然能打得很好。对"单人打牌"来说，这完全不是问题；但软件工程从来不是一个人的游戏，而是团队接力。

如果两个人合力打一手牌，你却把牌理得七零八落，队友就完全无法理解你的思路。同样，在软件工程中，文件随手扔桌面、不写接口定义、依赖 AI 随意生成代码——这些本质上就是在"乱放麻将牌"。它们没有解决任何**软件开发的本质困难（Essential Complexity）**，反而制造了大量**人为的、琐碎的困难（Accidental Complexity）**，极大地消耗了团队的精力。

更要命的是，大学之前的学习几乎全是单打独斗，而大学之后，我们必须像真实社会一样，学会与同学建立**既竞争又合作的"竞合"关系**。我们的代码不仅要今天能跑，更要让同伴看得懂，明天能改、后天能维护——这种长期演进的协作模式，对大一新生而言，是一种全新的心态挑战。

## 一、核心痛点与解决逻辑

针对上述挑战，我们不能靠口头劝导或机械禁令，而要通过 **"硬性工程约束（CI/CD）"**、**"命令行与文件系统基建（Missing Semester）"**、**"同侪协作机制（结对与 Review）"** 与 **"有趣且具挑战性的非罐头项目"** 五位一体来重构教学。

**解决链路：**

```
移动端原住民 + AI 依赖
    ⬇
CLI 基建 + 头文件先行
    ⬇
结对编程与 Peer Review
    ⬇
非罐头项目 + CI/CD 自动化构建
    ⬇
扎实的工程素养与 OOP 设计能力
```

## 二、破局 AI 依赖：扎实面向对象（OOP）功底

将考核重心从"程序运行成功"转移到"接口设计质量、抽象能力与底层原理理解"。

### 2.1 实施"头文件先行（Header-First）"防线

**做法：** 项目阶段一只允许编写 `.h` 头文件（定义类接口、成员变量访问控制、虚函数、封装关系），不允许写 `.cpp` 实现。

**目的：** 强制学生在不依赖 AI 补全具体实现逻辑的情况下，先思考类与类之间的"职责划分"与"契约设计"。头文件通过评审后，方可进行实现。

### 2.2 引入"代码答辩（Code Defense）"与多维度能力检验

**做法：**

- **抽查答辩：** 随机抽取 20% 的学生进行 3 分钟现场代码质询。问题聚焦于**课程已讲授的基础 OOP 概念**，例如：
  - "这个类为什么要用 `private` 封装这些成员变量？如果不封装会有什么问题？"
  - "解释一下这个构造函数在对象创建时做了什么？"
  - "这段代码违反了哪条 OOP 设计原则？可以怎么改进？"
  - "为什么这里要用 `const` 修饰成员函数？去掉 `const` 会有什么影响？"
- 回答不出者，作业得分打折；但允许学生在质询过程中**参考自己的代码**或**手绘简图**辅助说明。

- **纸面追踪（Paper Tracing）测验：** 随堂发放纸质试卷，上面印有一段短小的 C++ 程序（10-15 行，风格类似 LeetCode 简单题的核心逻辑，但去除算法难度），要求学生**仅通过人工推演，手写出程序执行完毕后的最终输出结果**。例如：

```cpp
#include <iostream>
using namespace std;

int main() {
    int sum = 0;
    for (int i = 1; i <= 5; i++) {
        if (i % 2 == 0) {
            sum += i * 2;
        } else {
            sum += i;
        }
    }
    cout << "Sum = " << sum << endl;
    return 0;
}
```

**学生只需在试卷上写出：** `Sum = 15`

此类题目考察的是**基础语法、循环逻辑和条件判断**的串联理解能力，而非算法技巧。代码不含类继承、虚函数、动态内存分配等进阶概念，确保大一新生在掌握基本控制结构后即可作答。AI 可以帮学生生成代码，但无法代替他们在考场上逐行推演执行过程。

纸面测试剥离了 IDE、AI 补全和编译器的辅助，迫使学生在**无外部支持**的环境下逐行推演代码语义，从根本上杜绝"代码跑通但脑子没跟上"的现象。判卷由助教统一完成，成绩计入平时分。

- **限时手写 / 无网机房测验：** 在实验室关闭外网/AI 插件，要求学生在 30 分钟内手写实现某个核心设计模式或内存管理接口。

**目的：** 通过"口头设计决策 + 笔头执行细节 + 综合实现能力"三层防线，消除学生"代码跑通即万事大吉"的侥幸心理，倒逼其理解 AI 生成的每一行代码。


## 三、弥合认知断层：从 Mobile-First 到 PC 操作系统与目录结构

补齐大学理论课常忽略的"Missing Semester"工程基本功，强迫学生建立起真实的"文件系统与路径"脑内图谱。

### 3.1 开学前两周："Missing Semester"工程基建通关营

**做法：** 借鉴 MIT 开创的《The Missing Semester of Your CS Education》课程理念——该课程旨在填补大学计算机科学理论教育与实际工业开发所需工具链之间的巨大鸿沟，涵盖 Shell、Git、调试、构建系统等被传统课堂忽视却至关重要的实战技能——前两周禁用一切图形化 IDE 的"拖拽式新建"，所有项目创建、目录切换、文件编译必须在终端（Shell/CMD）中完成。

**两周通关营详细日程：**

**第一周：文件系统与 Shell 基本功**

- **Day 1：告别桌面——文件系统树与路径遍历**
  - 让学生用 `tree` 命令打印整个用户目录，回答："你的桌面（Desktop）在树形结构中处于什么位置？它的父节点是谁？"
  - 作业：使用 `mkdir -p` 一次性创建三级目录 `project/include/utils`，并用 `cd -` 在最近两个目录间跳转。
  - 死路径红线：教学组提供脚本，扫描提交的代码中是否包含 `C:\Users` 或 `/home/xxx/Desktop` 等绝对路径模式，发现则拒绝接收。

- **Day 2：文件操作与通配符魔法**
  - 实战：给定混有 `.h`、`.cpp`、`.o`、`.tmp` 文件的杂乱目录，用一行 `mv *.h include/` 等命令完成分类归档。
  - 使用 `rename` 命令将 `Test_*.cpp` 批量重命名为 `unittest_*.cpp`。

- **Day 3：环境变量与 PATH 之谜**
  - 实验：通过 `which python` 与 `echo $PATH` 分析 Shell 如何找到命令。
  - 模拟故障：安装"假想工具"但故意不加入 PATH，让学生诊断并修复。

- **Day 4：输入输出重定向与管道**
  - 核心训练：使用 `>`、`>>`、`2>&1` 处理标准输出和错误输出；组合 `ps aux | grep code | wc -l` 统计进程数。
  - 工程应用：编写 `build.sh` 脚本，将编译输出同时显示屏幕并保存到 `build.log`（使用 `tee` 命令）。

- **Day 5：终端紧急编辑（Vim/Nano）**
  - 目标：不成为高手，但必须掌握在无图形界面服务器下修改配置文件的基本操作（`i` 插入、`ESC`、`:wq` 保存、`:q!` 退出）。
  - 场景考试：SSH 模拟连接远程服务器，发现 `CMakeLists.txt` 写错库名，限时 3 分钟用终端编辑器修复。

**第二周：版本控制与自动化构建**

- **Day 6：Git 本地工作流**
  - 概念破冰：将 Git 比作游戏"存档点"（`init`、`add`、`commit`、`log --oneline --graph`）。
  - 强制规范：提交信息必须遵循 `<type>: <subject>` 格式（如 `feat: add player move`），否则 CI 不通过。

- **Day 7：Git 远程协作与 PR 工作流**
  - 实操：Fork 教学组提供的"空项目骨架" → Clone 到本地 → 创建特性分支 → 修改后 Push → 发起 Pull Request。
  - 产出：将第一周所有 Shell 练习脚本整理成 `tools/` 目录，通过 PR 提交。

- **Day 8：CMake 入门**
  - 核心认知：CMake 是"编译器的生成器"，而非编译器本身。
  - 最小 `CMakeLists.txt` 解剖（含 `cmake_minimum_required`、`project`、`set`、`include_directories`、`add_executable`）。
  - 实践：在 `build/` 目录外执行 `cmake ..` 与 `make`，理解"外部构建（Out-of-source build）"的好处。

- **Day 9：包管理器与单元测试框架**
  - 场景：给项目引入 Google Test。演示系统级安装（`apt-get`）与项目级自动下载（`FetchContent`）。
  - 任务：为第一周的"统计 TODO 行数"脚本编写单元测试。

- **Day 10：综合实战——"Missing Semester 通关项目"**
  - 要求：项目名 `msc-project`，目录结构完全符合 `include/`、`src/`、`tests/` 分离；CMake 配置支持 `make test`；`README.md` 说明清晰；至少 3 条有意义 commit。
  - 验收：教学组提供自动化检查脚本，学生提交 GitHub 链接，脚本自动克隆、构建、运行测试并评分。

**强化练习贯穿两周：**

- 使用 `cd` / `ls` / `mkdir` / `tree` 等命令进行文件查找与管理。
- 将工程概念与数据结构课打通："目录就是一棵树（Tree Node），路径就是从根节点到目标节点的路径（Path Walk）"。
- 搞懂绝对路径与相对路径的区别（禁止出现类似 `C:\Users\...\Desktop\...` 的死路径）。

**教学支持与防挫败机制：**

- **"导航员"轮岗制**：由高年级学生或已掌握技能的同学每日值班，在 Discord/Slack 实时解答环境配置问题。
- **虚拟机镜像**：提供预装 Ubuntu、VS Code、Git、CMake、GCC/Clang 的 VirtualBox/VMware 镜像，避免"软件装不上"卡关。
- **进度追踪看板**：利用 GitHub Classroom 可视化每位学生的通关状态，连续两天落后自动发送提醒邮件。
- **"英雄贴"挑战**：每日 1-2 个附加题（如"用一行 Shell 命令找出所有大于 10MB 的文件并排序"），完成者获平时分加分。

### 3.2 建立硬性"自动化构建与零分红线"（CI/CD 机制）

**做法：** 引入标准工程目录结构，要求必须通过 Git 提交作业，并用 CMake 进行编译。

```
my_project/
├── CMakeLists.txt    # 自动化构建脚本
├── include/          # 存放 .h 头文件
├── src/              # 存放 .cpp 实现文件
├── tests/            # 单元测试
└── README.md         # 工程说明
```

**红线规定：** 不接受压缩包或桌面截图提交。统一提交到 GitHub/GitLab 仓库。运行自动测试脚本，如果无法通过 CMake 一键编译，或者路径依赖桌面，直接判定为 **0 分**。

## 四、引入同侪机制（Peer Accountability）：用社会学方法促进行为转变

利用优秀本科生重视同侪评价（Peer Recognition）的心理，将"不规范代码"转化为"对队友的直接困扰"，让 bad practice 无处遁形。

### 4.1 动态角色结对编程（Pair Programming）

**做法：** 两人一组，采用"驾驶员（Driver）与导航员（Navigator）"模式，且必须定期交换角色。

| 角色 | 职责 |
|------|------|
| **驾驶员（Driver）** | 负责键盘输入与代码编写 |
| **导航员（Navigator）** | 负责实时审计、提问与思考长远设计。当驾驶员盲目复制 AI 代码时，导航员必须现场质询；当驾驶员把文件保存在桌面时，导航员需要纠正 |

### 4.2 Pull Request 与代码互审（Peer Review）

**做法：** 代码合并至主分支前，必须经由结对队友的 Code Review 并 Approve。

**规范：** 若代码中包含桌面绝对路径、缺乏头文件封装、或提交日志混乱，队友有权且应该 Reject 该合并请求。

**效果：** 让坏习惯直接导致"队友无法 Build"，形成同侪压力，让坏习惯在团队内部被消化（如同"乱打麻将牌"会让队友直接拒绝合力打牌）。

## 五、拒绝"罐头项目"：设计有挑战、高趣味的大作业

废除 "标准贪吃蛇"、"简单化图书管理系统" 等在 AI 训练集中有海量模板的"罐头项目（Canned Projects）"。题目设计遵循 **"框架给定，插件自定义；解决一个实际小痛点、强约束、高扩展、自带同侪竞技性"** 原则。

### 5.1 项目一：面向对象智能体竞技场（Bot Battle Arena）

**设计：** 教学组提供一个开源的坦克大战或回合制卡牌游戏底座框架。学生需要利用 OOP 思想（继承、多态、策略模式、状态模式）编写属于自己的 Bot 逻辑接口。

**亮点：** 学生不写渲染逻辑，只写领域抽象。AI 无法一次性直接生成对抗逻辑；课程安排每周 CI/CD 自动举办 Bot 联赛，极大激发学生的工程好胜心。

### 5.2 项目二：Terminal Rogue-like 迷宫引擎

**设计：** 结合 CLI 终端训练，要求学生设计一个基于终端字符画的 Rogue-like 游戏引擎。

**亮点：** 强约束接口——玩家（Player）、怪物（Monster）、道具（Item）必须继承自同一个 `GameObject` 基类，并实现纯虚函数；地图加载必须通过相对路径读取文件，严禁硬编码。

### 5.3 项目三："代码考古"与 OOP 重构拯救计划

**设计：** 给定一份能够运行但完全写在一个文件中、充满全局变量与内存泄漏的 C 语言"烂代码"。要求学生用 OOP 设计原则重构为标准的 C++ 多文件工程，并用 Valgrind/Sanitizer 证明无泄露。

**亮点：** 训练学生的"代码阅读"与"架构整理"能力，直观体验从无序到有序的工程价值。

## 六、课程考核矩阵（推荐权重）

| 考核模块 | 权重 | 评分标准与规约 |
|----------|:----:|----------------|
| **Missing Semester 与 CI 构建** | 20% | Shell 命令操作、`include/`/`src/` 目录分离，CMake 一键编译无警告，Git Commit 规范 |
| **OOP 接口与设计** | 30% | 头文件设计合理性（封装性、继承抽象、接口隔离） |
| **结对协作与 Peer Review** | 20% | Git PR 互审记录、结对分工说明及同侪评价 |
| **代码答辩与原理质询** | 30% | 现场解释类设计逻辑、纸面追踪测验（手写代码输出与变量跟踪），确保真正掌握底座 |

## 七、总结

> **"规范的目录是工程的骨架，头文件是设计的思想，结对 Review 是工程文化的土壤。"**

通过"乱牌麻将"的比喻建立沟通共识，用命令行与 CMake 重塑文件系统直觉，用头文件与自动化 CI 强制工程骨架，用同侪 Review 滋养工程文化，用防 AI 罐头的竞技项目激发激情——这套方案旨在帮助 2026 级的大一新生迅速跨越习惯断层，成长为具备专业素养的软件工程师。

## 附录：方案核心理念一览

- ✅ **不是禁止 AI**，而是让学生具备质疑 AI 生成代码的能力
- ✅ **不是死记硬背**，而是通过工程约束倒逼理解
- ✅ **不是单打独斗**，而是通过同侪机制培养团队意识
- ✅ **不是罐头项目**，而是有竞技性、有挑战的真实工程体验
- 【注】 CS101 是用 OOP 还是 面向过程，还是用 Python...，另有文章讨论。
